HARI
====

Named after Hari Bahadur.

What we are building
--------------------
HARI is meant to become a small personal intelligence that grows with one person instead of trying to contain the whole internet inside one giant model.

The idea is simple:
- one HARI identity
- one long-lived personal memory
- one learned vocabulary and set of habits
- one growing library of skills
- many external tools when HARI does not know enough
- many possible bodies: phone first, then watch, computer, TV, and anything else that can expose useful capabilities

The body is replaceable. The learned person-specific state should not be.

A phone is our first real target because it already has microphone, speaker, camera, screen, contacts, apps, sensors, network, and it stays close to the person most of the day.

What exists today
-----------------
1. Native-language teaching
   HARI can be taught that a phrase means a concept without retraining a language model.

2. Personal memory
   Memories have cues, strength, importance, age, recall, reinforcement, and decay.

3. Habit learning
   Repeated choices become preferences only after enough evidence exists.

4. Skill learning
   HARI can be shown action sequences and infer reusable variable slots from multiple demonstrations.
   Example: show the same call procedure for Pratik and Mom, then generalize it to Dad.

5. Machine action language
   Human language is not executed directly. It becomes small typed actions such as FIND_CONTACT, VIDEO_CALL, OPEN_APP, SEND_MESSAGE, SHOW_NOTIFICATION, PLAY_MEDIA, RUN_CODE.

6. Safety gate
   Low-confidence actions are rejected. External side effects require confirmation before execution.

7. Tool routing
   HARI can choose between local and external capabilities and alter that choice after observing failures and successes.

8. Life state
   HARI has a persistent age counter and a small affect state used only to influence behavior. This is not a claim of consciousness or real human feelings.

9. Persistent state
   Language, memories, habits, learned skills, unfinished demonstrations, tool experience, affect, and age can survive process restart.

10. JSON protocol
    The current PHP prototype can be driven without a UI. This is deliberate: mobile/desktop/watch shells should talk to HARI through a narrow machine protocol rather than importing its internals.

11. Device mesh
    HARI now has the beginning of a many-body runtime. Devices advertise which machine actions they support. The same HARI action can be routed to a phone, watch, PC, TV, or future body. Routing can learn from success/failure and survives restart.

12. CI
    GitHub Actions checks syntax and behavior on supported PHP versions.

What is still fake / not built yet
----------------------------------
- no real Android app yet
- no actual phone calls/messages are being made by HARI
- no microphone input
- no wake word
- no speech recognition
- no natural Nepali voice
- no camera understanding
- no screen understanding
- no live accessibility bridge
- no JNI/C bridge
- no real Gemini/Codex/etc provider adapters yet
- no encrypted cross-device sync
- no production identity/security model
- no proof that HARI can learn an entire language from ordinary family use
- no proof of consciousness, feelings, anger, love, or subjective experience

The next target
---------------
PHONE BODY v0

Build a very small Android shell whose job is NOT to be HARI's brain.
Its job is to expose exact capabilities to HARI:

- app launch
- contacts lookup
- call intent
- message/share intent
- notifications
- media selection
- accessibility events/actions
- screen snapshots when symbolic UI data is insufficient
- microphone/speaker access
- camera frames on demand
- battery/network/device state

The Android side should translate between Android APIs and HARI's machine action language.
HARI should prefer exact OS APIs over visual guessing.

Order of execution preference:
1. OS/native API
2. app intent / deep link
3. accessibility semantic node
4. vision-assisted UI action
5. coordinate tapping only as last resort

After the phone bridge
----------------------
VOICE
- local wake detection
- speech recognition
- expressive speech output
- Nepali teaching/adaptation
- interruption and turn-taking
- vocal events such as chuckle, hum, whisper, short singing later

PERCEPTION
- screen events first, pixels only when needed
- camera only when requested or context explicitly permits it
- event-driven perception to save battery

TOOLS
- image generation provider
- coding provider
- web/research provider
- local utilities
- HARI chooses tools according to capability, cost, reliability, privacy and learned experience

MORE BODIES
Watch:
- notifications
- voice
- health/sensor surfaces if the owner explicitly permits them
- quick confirmations

Computer:
- files
- browser
- coding
- long tasks
- local compute

TV:
- media
- household display
- voice output

Future devices:
- anything that can expose a small, typed capability surface

Important architectural rule
----------------------------
HARI should not become one enormous model.
Neural systems should be used where ambiguity/generalization is necessary.
Normal software should be used where computers already know the answer exactly.

Do not use a neural model to calculate what the OS can return exactly.
Do not use vision to find a button when accessibility exposes the button semantically.
Do not pretend an action succeeded until the machine confirms it.
Do not pretend HARI knows something when confidence is low.

Long-term test
--------------
A fresh HARI should be generic.
A HARI that has lived with one person for years should know that person's words, routines, family relationships, preferred explanations, devices, habits and learned procedures.

The difficult experiment is whether that accumulated personal history can make a small HARI more useful to its owner than a much larger generic assistant that has never met them.

Current status
--------------
This is still a research kernel, not a product.
The important parts now are real enough to test: memory, teaching, habits, skill induction, safe action plans, tool routing, persistence, and multi-device routing.

Next engineering boundary: connect the machine action layer to a real Android body without polluting HARI's portable core with Android-specific assumptions.
